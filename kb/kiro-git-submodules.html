🔗 Kiro + Git Submodules para Organizaciones

Cómo Kiro recomienda estructurar repositorios compartidos entre equipos usando Git Submodules y Multi-root Workspaces

📄 Fuente: kiro.dev/docs/specs/best-practices · kiro.dev/docs/editor/multi-root-workspaces · kiro.dev/blog/multi-root-workspaces
01 — El problema que resuelven los submodules en Kiro

🏢 Escenario organizacional típico

Múltiples equipos comparten specs, steering files y componentes. Sin una estrategia, cada proyecto duplica o diverge.

📦team-a/app
→
📐shared/specs
←
📦team-b/app
↓
🏛️central-specs-repo
fuente de verdad

✅ Cuándo usar Git Submodules con Kiro

  • ✓ Shared libraries: editando una feature que requiere cambios en una librería compartida
  • ✓ Microservicios: manteniendo frontend + backend + auth relacionados
  • ✓ Specs compartidas: múltiples proyectos referencian las mismas especificaciones
  • ✓ Refactor cross-repo: navegar y refactorizar a través de varios proyectos a la vez
  • ✓ npm/yarn/pnpm workspaces: monorepos con múltiples paquetes
02 — Recomendación oficial de Kiro para specs compartidas

📋 3 pasos recomendados por Kiro (kiro.dev/docs/specs/best-practices)

1
Repositorio central de specs
Crear un repo dedicado para especificaciones compartidas que múltiples proyectos puedan referenciar.
2
Git Submodules / Package References
Vincular las specs centrales a proyectos individuales usando submodules, package references o symbolic links.
3
Workflows cross-repo
Desarrollar procesos para proponer, revisar y actualizar specs compartidas que afectan múltiples proyectos.
03 — Estructura de archivos recomendada

📁 Workspace Single-Root (básico)

📁 my-app/ ├── .kiro/ ← specs, steering, hooks │ ├── specs/ │ │ ├── 001-auth/ │ │ └── 002-dashboard/ │ ├── steering/ │ └── hooks/ ├── src/ └── tests/

Configuración estándar. Todo el contexto de Kiro vive bajo .kiro/ en la raíz del proyecto.

📁 Multi-root Workspace (organizacional)

📁 my-app/ ← Root 1 │ └── .kiro/ 📁 shared-ui/ ← Root 2 (submodule) │ ├── .kiro/ │ └── components/ 📁 auth-service/ ← Root 3 (submodule) │ ├── .kiro/ │ └── api/ 📁 central-specs/ ← Root 4 (repo central) └── .kiro/specs/

Cada root mantiene su identidad. Kiro unifica specs, steering y hooks en una sola vista.

04 — Cómo Kiro gestiona cada artefacto en Multi-root

📋 Specs

  • ✓ Lista unificada de todos los roots
  • ✓ Muestra el root de origen junto a cada spec
  • ✓ Kiro determina el root correcto al crear una spec nueva
  • ✓ #spec:nombre funciona cross-root

🎯 Steering Files

  • ✓ Always Included: se cargan sin importar el root activo
  • ⚡ Conditional: solo si el agente trabaja en ese root
  • ✓ Global steering aplica a todos los workspaces
  • ✓ Workspace steering aplica solo a ese root

🪝 Hooks

  • ✓ Lista unificada, cada hook muestra su root
  • ⚡ File hooks solo se disparan para archivos del mismo root
  • ✓ Aislamiento limpio: cambios en shared-ui no disparan hooks de my-app

🔌 MCP Servers

  • ✓ Todos los MCP de todos los roots se inicializan al arrancar
  • ⚡ Si dos roots definen un MCP con el mismo nombre, gana el último root
  • ✓ Buena práctica: usar prefijos — frontend-github vs backend-github

🔍 Búsqueda y Contexto

  • ✓ #codebase busca en todos los roots simultáneamente
  • ✓ Indexación automática de código, docs y configs de cada root
  • ⚡ Si hay archivos duplicados (ej: utils/logger.ts en 2 roots), Kiro muestra lista con paths completos
  • ✓ Soporte de rangos: #file:src/index.ts:10-25
05 — Cómo configurar un Multi-root Workspace con Submodules

⚙️ Pasos de configuración

Opción A — Desde la UI de Kiro

1
Abrir el proyecto principal en Kiro
2
File → Add Folder to Workspace... y seleccionar el submodule o repo compartido
3
Kiro reconoce cada carpeta como root y carga los .kiro/ de cada uno

Opción B — Drag & Drop

1
Arrastrar otra carpeta de proyecto desde el explorador de archivos
2
Soltarla en el panel Explorer de Kiro
3
Kiro carga automáticamente specs, steering y hooks del nuevo root

Agregar el submodule en Git (terminal)

# Agregar repo de specs compartidas como submodule git submodule add https://github.com/org/central-specs.git shared/specs # Clonar un repo que ya tiene submodules git clone --recurse-submodules https://github.com/org/my-app.git # Actualizar submodules existentes git submodule update --remote --merge
06 — Ejemplo real: workflow cross-project con Kiro

🎬 Caso de uso: actualizar un componente compartido y su consumidor

Escenario: actualizar el componente Button en shared-ui y luego actualizar my-app para usar la nueva prop variant.

1
Abrir my-app y shared-ui en un mismo workspace multi-root
2
Pedirle a Kiro:
#spec:ui-update Add 'outline' variant to Button, then update my-app to use it
3
Kiro trabaja en ambos roots en una sola conversación: actualiza código, dispara hooks y trabaja con specs
4
Sin cambiar de ventana ni crear conversaciones separadas

Estructura del workspace en este escenario:

📁 my-app/ ← Root 1 │ ├── .kiro/specs/ │ │ └── ui-update/ │ └── src/components/ 📁 shared-ui/ ← Root 2 (submodule) │ ├── .kiro/ │ └── components/ │ └── Button.tsx

Kiro indexa ambos roots y puede referenciar archivos de cualquiera de los dos en la misma sesión.

07 — Comparativa de estrategias de repositorio
Estrategia Cuándo usar Ventajas con Kiro Consideraciones Soporte Kiro
Single Repo Proyecto pequeño, un equipo Setup mínimo, todo en un .kiro/ No escala bien entre equipos Nativo
Git Submodules Specs/libs compartidas entre proyectos Multi-root workspace unifica contexto; cada root mantiene su .kiro/ Requiere disciplina en actualizaciones de submodules Recomendado
Package References Librerías versionadas (npm/yarn workspaces) Compatible con multi-root; ideal para componentes con versioning semántico Overhead de publicación de paquetes Soportado
Symbolic Links Desarrollo local, sin CI/CD complejo Funciona con multi-root si los paths son correctos Frágil en CI/CD y Windows Condicional
Monorepo puro Organización con control total del toolchain Multi-root puede apuntar a subdirectorios del monorepo Requiere herramientas adicionales (Nx, Turborepo) Parcial
08 — Buenas prácticas para organizaciones

📐 Specs

  • ✓ Un repo central para specs compartidas entre equipos
  • ✓ Specs por feature, no una sola spec para todo el proyecto
  • ✓ Versionar specs junto al código que describen
  • ⚡ Proceso definido para proponer cambios a specs compartidas (PR + review)

🎯 Steering Files

  • ✓ Global steering para estándares de toda la organización
  • ✓ Workspace steering para convenciones específicas del proyecto
  • ⚡ Workspace-level tiene precedencia sobre global cuando hay conflictos
  • ✓ Usar inclusion: fileMatch para steering condicional por tipo de archivo

🔌 MCP Servers

  • ✓ Usar prefijos en nombres: frontend-github, backend-github
  • ✗ Evitar nombres genéricos que colisionen entre roots
  • ✓ Config a nivel usuario para MCPs globales de la organización
  • ⚡ El último root en el workspace "gana" si hay nombres duplicados

📂 Cómo Kiro carga el contexto en un proyecto

Al abrir proyecto-alpha como multi-root workspace con org-standards:

1° Global steering — ~/.kiro/steering/ del usuario
↓ se combina con
2° Org steering — org-standards/.kiro/steering/
↓ se combina con
3° Área steering — org-standards/submodules/area-*/
↓ se combina con
4° Proyecto steering — proyecto-alpha/.kiro/steering/ (mayor precedencia)

⚙️ Comandos Git para este modelo

# 1. En org-standards: agregar cada área git submodule add https://github.com/org/area-dev-agents.git \ submodules/area-dev-agents git submodule add https://github.com/org/area-qa-agents.git \ submodules/area-qa-agents # ... repetir por cada área # 2. En un proyecto nuevo: importar org-standards git submodule add https://github.com/org/org-standards.git \ org-standards # 3. Clonar proyecto con toda la cadena git clone --recurse-submodules \ https://github.com/org/proyecto-alpha.git # 4. Actualizar org-standards en el proyecto cd org-standards git pull origin main cd .. git add org-standards git commit -m "chore: update org-standards to latest"

⚖️ Reglas de precedencia y responsabilidades por capa

Capa Repo Qué define Quién puede modificar Precedencia en Kiro
🌐 Global ~/.kiro/steering/ Preferencias personales del desarrollador Cada desarrollador Baja
🤖 Área area-*-agents Estándares del capítulo (dev, qa, po, security, ba) Chapter Lead del área Media-baja
🏛️ Organización org-standards Constitution, arquitectura, seguridad, workflow Arquitectura / Tech Lead Media
📦 Proyecto proyecto-*/ Overrides locales, reglas específicas del dominio Equipo del proyecto Alta (gana)

⚡ En Kiro, el steering del workspace (proyecto) tiene mayor precedencia que el global cuando hay conflictos. Los proyectos pueden extender o sobreescribir reglas de org-standards sin modificar el repo central.
